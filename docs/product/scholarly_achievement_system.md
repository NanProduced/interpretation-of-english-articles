# Scholarly Achievement System

## 1. 背景与目标

为了提升用户的长期留存率与每日阅读动力，我们将原本枯燥的“统计数据”升级为一套具有品牌仪式感的“勋章进化系统”。该系统旨在通过视觉化的成长路径，回馈用户的学术投入。

## 2. 核心概念

### 2.1 账户身份：标准学者 (Standard Scholar)

目前作为小程序所有用户的统一默认身份。

- **存在理由与设计用意**：
  1. **权限锚点 (Permission Anchor)**：它是系统功能的“通行证”标识，直接关联用户的服务配额（如每日 300 积分的刷新逻辑）。
  2. **身份宇宙观 (Psychological Identity)**：通过将 Generic 的“普通用户”具象化为“学者”，建立产品与用户之间的学术情感纽带，强化“读书手账”的产品隐喻。
  3. **商业扩展空间 (Scalability)**：它是分级体系的入口。预留此位置是为了在未来上线付费订阅时，能无缝切换为“高级研究员”或“荣誉学者”，而不必重构页面顶部的视觉中心。
  4. **差异化定位**：勋章代表\*\*“勤奋度（已读篇数）”**，而身份标签代表**“服务级别（权限等级）”\*\*。两者双轨并行，形成完整的激励与服务矩阵。

### 2.2 视觉进化勋章 (Evolutionary Medals)

勋章会根据用户的累积阅读表现，在**物理形态、核心色彩、交互光泽**三个维度发生进化。

## 3. 交互与动效设计

- **封蜡呼吸 (Medal Glow)**：勋章容器具有一个周期为 4s 的呼吸动画，模拟在高克重纸张上的封蜡印章质感。
- **墨水脉冲 (Ink Pulse)**：当仪表盘数值正在同步时，数字会以淡化的呼吸态显示，避免生硬的空白。
- **自适应排版**：所有功能图标均具备 `flex-shrink: 0` 保护，确保在任何屏幕及长文本压力下，勋章的物理形态不发生扭曲。

## 4. 关键逻辑修正：持久化阅读统计

针对“删除历史记录导致勋章降级”的痛点，我们提出以下逻辑优化建议：

### 4.1 核心逻辑调整

- **现状**：篇数统计 = `count(history_records)`。
- **目标**：篇数统计 = `user_profile.cumulative_reading_count`。
- **策略**：勋章等级应基于**用户累积贡献**而非**当前归档存量**。

### 4.2 后端协作要求 (Technical Requirement)

我们需要后端在用户信息/配额接口中增加以下字段：

1. `cumulative_article_count` (int): 记录该用户自注册以来的所有已成功解析的文章总数，且**不可逆**（删除 history 表中的记录不应导致此字段减小）。
2. `cumulative_word_count` (int): (可选) 累积学习的单词总数。

## 5. 邀请奖励功能（Invite & Reward）

### 5.1 微信小程序能力调研

<aside>
✅

**结论：可以实现“被邀请人点击并注册才发放奖励”的逻辑。** 核心路径是“被邀请人侧验证”，而非依赖分享者侧回调。

</aside>

**可行的技术路径：**

1. **分享时携带参数**：在 `onShareAppMessage` 中，通过 `path` 参数附带邀请者 ID，例如 `path: '/pages/index?inviter=user123'`
2. **被邀请人打开时读取参数**：新用户通过分享卡片进入小程序时，在 `App.onLaunch` 或 `App.onShow` 的 `options.query` 中可以拿到 `inviter` 参数
3. **后端校验并发放奖励**：新用户完成注册后，后端校验新用户身份 + 邀请者有效性 + 防重复绑定，全部通过后发放积分

**平台限制（需注意）：**

- 微信自 2018 年起取消了分享回调中的 `success` / `fail`，即 **无法在分享者侧判断用户是否真正完成了分享动作**
- 但这对我们的需求没有影响，因为判定逻辑在被邀请人侧完成——只要新用户带着 `inviter` 参数进入并注册，后端即可确认邀请关系

### 5.2 MVP 实现方案

**MVP 原则**：最小闭环，砍掉一切非必要复杂度。

**功能边界：**

- 奖励只给邀请者，不给被邀请者（后续再做双向奖励）
- 奖励形式统一为积分（Credits），复用现有积分体系
- 每个用户最多邀请 **10 人** 获得奖励（硬上限，防刷且控制积分通胀）
- 一个新用户只能归属一个邀请者，以首次进入时携带的 `inviter_id` 为准
- **奖励数额建议**：1 次成功邀请 = 1 次免费解读的积分量（与成本模型对齐，用户心智清晰：“邀请一个朋友 = 白赚一篇解读”）

**UI 范围：**

- 一个“邀请好友”按钮 + 一个“已成功邀请 X 人”计数器
- 不做排行榜、邀请列表等复杂功能

**后端字段预设：**

| 字段                        | 类型            | 说明                      |
| ------------------------- | ------------- | ----------------------- |
| `inviter_id`              | string / null | 谁邀请了我，注册时写入，不可变更        |
| `successful_invite_count` | int           | 我成功邀请了几人，每次被邀请人注册成功后 +1 |

**实现流程：**

1. 邀请者点击“邀请好友”→ 触发 `onShareAppMessage`，`path` 拼接 `inviter_id`
2. 被邀请人点击分享卡片进入小程序 → `onLaunch` 读取 `query.inviter`，缓存到本地
3. 被邀请人完成注册 → 注册 API 将 `inviter_id` 提交后端，写入邀请关系表
4. 后端校验（新用户 + 有效邀请者 + 未重复邀请 + 未超上限）→ 给邀请者加积分

## 6. 评审要点

1. **视觉一致性**：确认勋章图标的线条粗细是否与全局 Lucide 图标集一致。
2. **邀请奖励与成本模型对齐**：确认单次邀请奖励积分值是否与单次解读成本匹配。
3. **防刷策略**：确认 10 人上限在 MVP 阶段是否充分，是否需要增加频率限制（如每日上限）。
