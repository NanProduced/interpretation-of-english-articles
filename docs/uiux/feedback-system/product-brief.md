# Feedback Product Brief

## Feature Summary

反馈系统帮助用户在阅读过程中报告解析、标注、词典和应用体验问题，并让团队能评审、修正、奖励与回传结果。它的价值不只是“收集意见”，而是建立一个低打扰、可追踪、能沉淀数据的质量闭环。

## Primary User Action

用户在发现问题时，应能用最少步骤提交带上下文的反馈；提交后，应知道反馈已被记录，以及之后可以在哪里查看处理状态。

## Design Direction

反馈体验应延续 Claread 的“阅读优先、安静、精确、纸感”方向。

- 在阅读流中，反馈入口像页边小动作，不像客服广告位。
- 反馈表单使用底部 sheet 或独立页面，不使用窄侧栏。
- 分类选项应像清晰的表单控件，不像一组拥挤卡片。
- 成功状态要克制但明确，避免只靠 toast。
- “我的反馈”要像处理记录，不像消息中心或任务中心。

## User Mindset

用户打开反馈时通常处于三种状态：

| State | 典型场景 | 设计要求 |
| --- | --- | --- |
| 快速认可 | 标注或整篇解析确实有帮助 | 一键完成，不要求输入 |
| 发现具体问题 | 某个释义、标注、句子解析不对 | 自动带上下文，用户只选问题类型 |
| 主动建议或报 bug | 从设置页进入反馈 | 提供完整文本输入和“我的反馈”入口 |

## Experience Principles

1. **入口轻，表单稳。** 阅读中只显示轻量入口，点开后再给完整表单。
2. **分类先于长文本。** 对解析类反馈，先选结构化问题，再补充说明。
3. **上下文自动采集。** 不让用户复述是哪篇文章、哪个单词、哪条标注。
4. **状态可见。** 提交后在“我的反馈”可查，不让反馈进入黑箱。
5. **奖励安静到账。** 采纳后可发积分，但不打扰用户，不使用推送作为默认机制。
6. **正负反馈分开。** “有帮助”是快速动作，“不准确/反馈”才打开细分表单。

## Key States

| State | Required UX |
| --- | --- |
| Idle | 入口低调，不抢阅读主层级 |
| Selecting | 分类可清楚区分，已选状态明确 |
| Disabled | 说明为什么不能提交，例如“请选择问题类型” |
| Submitting | 防重复点击，按钮显示提交中 |
| Success | 显示已记录，可去“我的反馈”查看 |
| Error | 保留用户输入，允许重试 |
| Duplicate/upsert | 告知“已更新你的反馈”，不要制造重复记录 |
| Reviewed | 用户侧显示已采纳/已解决/已关闭和简短说明 |
| Rewarded | 用户侧显示奖励积分，积分明细可追溯 |

## Design Risks

- 把反馈做成大面积卡片，会破坏阅读沉浸。
- 左侧抽屉在小程序 viewport 中太窄，容易产生压迫感和层级混乱。
- 只写入数据库但不给用户状态，会让反馈像黑箱。
- 只展示“待处理/已采纳”等后台词，缺少用户可理解的处理结果。
- 分类过多会提高选择成本，尤其在阅读流里。
